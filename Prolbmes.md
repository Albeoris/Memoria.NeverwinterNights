## Отчёт: потенциальные точки конфликта между модами разных авторов

Ничего не исправлял, только нашёл и задокументировал. Разбито по серьёзности.

### 1. ESI-ключи инъекций — «числа-как-бы-строки» без реестра уникальности (самое серьёзное)

`ESI_InjectToObject(oObject, sKey, nHandler, sScript, nPlacement)` в `esi_lib.nss:159-172` хранит инжектированный скрипт в JSON-карте `jScripts`, ключ — это `sKey` **как есть**: `JsonObjectSet(jScripts, sKey, JsonString(sScript))`. Если два разных мода передадут одинаковый `sKey` для одного и того же `(nHandler, nPlacement)`, второй **молча перезапишет** обработчик первого — без ошибки, без предупреждения.

Ключи сейчас выбираются авторами вручную как голые числа, а не как неймспейс-строки:
- `melse_lib.nss:106-111` — `MELSE_INJECT_KEY_* = "100"`, `"200"`, `"300"`, `"400"`, `"410"`, `"500"` — короткие круглые числа, максимально велика вероятность, что другой автор (или даже будущий мод в этом же репозитории) выберет то же самое.
- `mecalm_lib.nss:10` — `MECALM_ESI_INJECTION_KEY = "9317"`.
- `metact_core.nss:9` — `METACT_ESI_KEY = "7421"`.
- `memoria_config.nss:399` — литерал `"config"`, ещё более вероятное совпадение с чужим мод (весьма «обычное» слово).
- Даже собственный README ESI показывает пример `"acme_evt"` — то есть правильный паттерн (неймспейс-строка) существует, но CALM/TACT/LSE/Config ему не следуют.

Дополнительно: если `sKey` числовой (`^[0-9]+$`), значение параллельно кладётся в «псевдо-массив» через `RAV_SetLocalArrayString(oObject, ..., StringToInt(sKey), sScript)` (`esi_lib.nss:172`) — то есть число буквально используется как индекс массива, а не просто как имя.

### 2. Полная перезапись базовых скриптов движка (плоское пространство имён override)

LSE полностью подменяет собой файлы `nw_c2_default1.nss`, `nw_c2_default5.nss`, `nw_c2_defaultb.nss` (LootingSystemEnhanced/source) — это одни из самых часто кастомизируемых скриптов ИИ существ в модулях NWN. Поскольку override-каталог — плоское пространство имён (один resref = один файл), **любой другой мод/модуль, который тоже переопределяет эти же скрипты, полностью «выигрывает» или полностью «проигрывает»** — конфликт решается не слиянием, а победой последнего загруженного файла целиком.

`default.ncs` — та же история, но уже осознанно задокументирована в `AGENTS.md` как «только MEBOOTSTRAPPER может его предоставлять»; тем не менее это всё ещё жёсткая точка конфликта с любым сторонним (не-Memoria) паком, который тоже кладёт свой `default.ncs`.

### 3. Дубли `id` в реестрах модов — два независимых механизма с разной защитой

- В Bootstrapper (`MEBOOTSTRAPPER_DiscoverEntries`, `memoria_boot.nss`) дубликат `id` из `memoria_*.txt` хотя бы **обнаруживается** (`MEBOOTSTRAPPER_HasId`) и один раз пишется предупреждение игроку — но третий/второй мод с тем же `id` просто не подключается, тихо.
- В `MEMORIA_CONFIG_LoadModules()` (`memoria_config.nss`) для `mconfig_*.txt` **вообще нет проверки на дубли `id`**. `MEMORIA_CONFIG_GetSelectedModule` ищет первое совпадение по `id` в отсортированном по имени массиве — если два разных `mconfig_*.txt` от разных авторов совпадут по `id`, второй мод навсегда останется недоступен в UI конфигурации (не просто перезаписан — не выбираем никогда), и что хуже — сохранение настроек может применяться не к тому мод(у), если имена/сортировка совпадут по порядку.

### 4. Тег предмета `MEMORIA_CONFIGURATION_ITEM` с деструктивным побочным эффектом

`MEMORIA_CONFIG_EnsureItem` (`memoria_config.nss`) находит предмет по тегу `GetItemPossessedBy(oPC, MEMORIA_CONFIG_ITEM_TAG)`, и если у найденного объекта не тот `MEMORIA_CONFIG_LOCAL_ITEM_SCHEMA` — **вызывает `DestroyObject(oItem)`**. Если сторонний мод/автор случайно создаст предмет с тем же тегом (`"MEMORIA_CONFIGURATION_ITEM"`) для других целей, Configuration Manager его уничтожит.

### 5. Завязка на строковый индекс диалог.tlk №3 для определения языка

Во всех `*_is_ru.nss` (`mecalm_is_ru.nss`, `metact_is_ru.nss`, `meconfig_is_ru.nss`, `meboot_is_ru.nss` если добавлен) язык определяется сравнением `GetStringByStrRef(3) == "Барды"`. Это жёстко зашитая зависимость от конкретного номера строки ванильного `dialog.tlk`. Любой сторонний мод/локализационный патч/тотал-конверсия, меняющий строку №3 в TLK, ломает автоопределение языка сразу во **всех** модах Memoria.

### 6. Кастомный TLK-офсет в LSE (Ravick-система локализации)

`RAV_GetStringByStrRef` в `rav_util.nss:130-133` читает `GetStringByStrRef(RAV_STRREF_BASE + RAV_STRREF_OFFSET + nStrRef)`, где `RAV_STRREF_OFFSET = 0` — то есть «сырые» номера строк кастомного `custom.tlk` модуля используются напрямую. Если модуль или другой мод тоже пишет в `custom.tlk` и их диапазоны индексов пересекаются с числами, которые использует LSE (`nStrRef` из `melse_text_*` — там задействован диапазон 1-999), возможна путаница/подмена строк.

### 7. Жёстко забитый номер strref 6416 в TACT UI

`metact_ui.nss:81` и `metact_ui.nss:268`: `GetStringByStrRef(6416 + iRating)` — подписи для «рейтинга противника» берутся напрямую из ванильных строк `dialog.tlk` по номеру. Модуль с модифицированным `dialog.tlg`/TLK (частая практика в кастомных рулсетах) выведет неверные подписи.

### 8. Идентификаторы NUI-окон в общем пространстве на клиенте игрока

Строки вроде `"memoria_config"` (`MEMORIA_CONFIG_WINDOW_ID`), `"meconfig_cache"`, `"meboot_cache"` — идентификаторы NUI-окон общие на клиента, без встроенной защиты от совпадения с окном другого (не-Memoria) мода. `NuiFindWindow`/`NuiDestroy` по такому ID при совпадении может закрыть/подхватить чужое окно.

### 9. Второстепенное / более низкий риск
- Теги эффектов вроде `MECALM_LOCK_GLOW_9F31` — риск ниже (есть случайный суффикс), но при совпадении с чужим тегом эффекта возможен цикл `RemoveEffect` по чужому эффекту в `MECALM_ClearHighlight`.
- `memoria_item.nss` читает имена через `Get2DAString("classes"/"metamagic", "Name", iRow)` по номеру строки — при кастомизации `classes.2da`/`metamagic.2da` сторонним контентом возможна путаница с именами (зависит от вызывающего кода, передающего `iRow`).
- Resref общих ресурсов (`memoria_config` предмет и т.п.) — тот же класс риска, что и п.2/3, но с гораздо более специфичным именем, поэтому вероятность ниже.



Готово — отчёт выше, изменений в код не вносил.
